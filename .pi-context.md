# r8152-fix project context for pi

## What we're doing
Fixing TP-Link UE300 (Realtek RTL8153) USB Ethernet that keeps crashing with `Tx status -71` on OpenRoyleAl's Surface Pro (i5-7200U, no USB-C, 1 USB-A port).

## Latest state
- Kernel: 6.18.7-surface-1, r8152 driver v1.12.13
- Device: `2357:0601` on Bus 002 (USB 3.0), `/sys/devices/pci0000:00/0000:00:14.0/usb2/2-1/2-1.4`
- Interface: `enx3c52a1b7d70d`
- Repo: https://github.com/OpenRoyleAl/tp-link-ue300-r8152-fix
- Local clone: ~/r8152-fix/

## Fixes applied (last session, May 4 2026)
1. **Disable all 10 offloads:** tso, gso, gro, sg, rx-vlan-offload, tx-vlan-offload, rx-checksum, tx-checksum-ipv4, tx-checksum-ipv6, eee
2. **USB 2.0 quirk:** `usbcore.quirks=2357:0601:b` set via sysfs + added to GRUB
3. **Watchdog:** runs every 1 min, detects errors in 2 min window, threshold >5 errors, driver unbind/bind then port power cycle, lock file prevents races
4. **Systemd service + udev rules** installed

## Script files
- `fix-r8152.sh` — main installer/uninstaller/status (has watchdog embedded in `create_watchdog()`)
- `r8152-watchdog.sh` — standalone watchdog (generated by fix-r8152.sh, also tracked in git)

## Key paths
- Watchdog log: `/tmp/r8152-watchdog.log`
- Fix log: `/tmp/r8152-fix.log`
- Restart marker: `/tmp/r8152-watchdog-last-restart`
- Udev rule: `/etc/udev/rules.d/99-r8152-fix.rules`
- Systemd service: `/etc/systemd/system/r8152-fix.service`

## Common commands
```bash
# Check status
sudo bash ~/r8152-fix/fix-r8152.sh status

# Re-apply fixes
sudo bash ~/r8152-fix/fix-r8152.sh apply

# See watchdog history
tail -30 /tmp/r8152-watchdog.log

# Check errors right now
journalctl -k --since "10 minutes ago" | grep -c "r8152.*Tx status -71\|r8152.*Stop submitting\|r8152.*timed out"
```

## If user says "it crashed again"
1. Run `sudo bash ~/r8152-fix/fix-r8152.sh status` and show output
2. Check `tail -30 /tmp/r8152-watchdog.log`
3. Check `journalctl -k --since "30 minutes ago" | grep -i r8152 | tail -20`
4. Determine if more offloads need disabling or if hardware is truly faulty
5. If watchdog loop detected, suggest moving recovery to port power cycle first
6. If device keeps failing even with USB 2.0 quirk + all offloads, recommend AX88179-based adapter
